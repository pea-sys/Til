# 要件定義の極意チェックリスト

## 機能不全を防ぐ極意

### Rule1.業務フローを起点にする

- 担当者が作業できる粒度にする
  - [ ] 「誰が、どのツールで、どの手順で、何を根拠に、何を出すか」を書いている
  - [ ] そのフローだけを読んで、初見の担当者でも実行できる
- インプットとアウトプットを把握する
  - [ ] 各工程の入り口（受領物）と出口（成果物）を具体名で記録している
  - [ ] そのアウトプットが次の工程で実際に参照されている証跡がある
  - [ ] 使われていないアウトプットがない
- 判断基準と処理ルール
  - [ ] 作業ボリュームが把握できている
  - [ ] 例外時の代替手段を明記している
  - [ ] システム化可否を検討した（自動判定、人判断、ハイブリット）
- 作業ボリュームの把握
  - [ ] 平常時・繁忙期の件数と処理時間を数値で記録している
  - [ ] 担当人数と同時並行数、ボトルネット工程は特定できている
- 拝啓と目的の確認
  - [ ] 業務の目的と価値を言語化している
  - [ ] 目的に対する成果指標を確認している

### Rule2.現場の声を直接取り入れる

- 「あったら便利」ではなく、本当に使われる機能に絞る
  - [ ] 機能追加の効果を定量、定性で説明できる
  - [ ] 実際に業務で使うことを確認した
  - [ ] この機能が必要ということを現場で議論した

- 要件確認は、全体より個別に確認する
  - [ ] 個別ヒアリング要約を当人確認(同意・日付)まで取る
  - [ ] 役割別1on1+現場シャドーイングで裏側の例外を拾う

- 定性情報を定量化することで判断材料に変える
  - [ ] 作業をすべて定量的に可視化しているか
  - [ ] 4軸(件数、頻度、影響範囲、時間)で数値化し、目標を整理する
- 「確認したつもり」「聞いたつもり」を潰すコミュニケーションをとる
  - [ ] 当事者の口で操作手順を説明できるか
  - [ ] 代表データ+境界値で通しで確認してもらったか

* 暗黙知を引き出し設計に活かす
  - [ ] すべての分岐／判断についてロジック、必要なデータが可視化する
  - [ ] 分岐／判断ロジックについて例外を確認しているか

### Rule3.「超具体的なユースケース」に落とし込む

- ユースケースを業務フロー基準で作成する
  - [ ] ユースケースの前提となる業務フロー（開始～終了・分岐・例外）が整理されている
  - [ ] 画面単位・昨日単位の操作ではなく、「業務の筋道」として成り立つ粒度で書けている
- ユーザー単位のシナリオに分解する
  - [ ] ユースケースが「誰のシナリオか」を明確に書いている
  - [ ] 複数ロールの操作が１つのユースケースに混ざっていない
  - [ ] 各ユーザーのやること／やらにことがユースケース上で見分けられる
- システム外の動きを含めて描写する
  - [ ] 紙・Excel・口頭確認・事前のメモ書きなど、捜査前後の現実の業務が記述されている
  - [ ] システム化しない作業がリストアップされシステム外業務が明確に判断できている
- 入出力情報を具体的に書く
  - [ ] 入力情報が「何を、どこから、どの形式で」取得されるかを明記されている
  - [ ] 出力情報が「何を、どんな形式で、誰がどう使うか」まで記載されている
  - [ ] 入出力を具体化した結果、不足情報、不要な画面・出力・項目を削除する判断ができている

### Rule4.動くプロトタイプで具体化する

- 業務シナリオに沿った流れとして組み立てる
  - [ ] 代表的な業務シナリオを、プロトタイプ上で最初から最後まで途切れずに辿れる
  - [ ] 利用者が画面遷移で迷子にならずに、卯木に何をすればよいかが自然に分かる
- 利用者が自分の業務として受け取れる表現にする
  - [ ] 表示される用語・データ例が、現場の業務ドメイン（商品・顧客・金額など）に近い
  - [ ] 利用者が画面を見たときに、これは自分たちの業務だと違和感なく受け取れている
  - [ ] プロトタイプで説明した内容を、そのまま現場の会話や社内説明に使えるレベルになっている
- 現場を巻き込む「体験レビュー」の場を設計する
  - [ ] レビューで説明主体ではなく、利用者に実際の業務シナリオを操作してもらう時間を確保している
  - [ ] 捜査中の迷いや一時停止など、口に出されていない戸惑いを観察・記録する役割の人がいる
  - [ ] レビュー後に「やってみてどうだったか」を業務目線で振り返る時間をとっている
- 作る手段は本物にこだわらない
  - [ ] 本番技術に縛られず、ノーコード／簡易ツールなどで業務の流れが分かるレベルを素早く用意している
  - [ ] 実装の都合ではなく、業務がイメージできるかどうかをプロトタイプの完成ラインとして定義している
  - [ ] 変更へ作り直しが前提のラフなプロトタイプで、早い段階から現場に当てている

### Rule5.要件の意思決定は確実に現場がする

- 「提案者」ではなく「翻訳者」として機能する
  - [ ] IT部門は判断の主導権ではなく、判断の支援役として現場と向き合っている
  - [ ] 表や一覧で役割分担が整理されている（例えば、ビジネス判断・技術判断・共同判断の分類など）
- 意思決定のために「わかる情報」をそろえて提供する
  - [ ] 「この資料を見て、何を判断すればよいか」が明確に示されている
  - [ ] プロトタイプや画面一覧、業務フロー・画面一覧など、構造化された資料で判断支援されている
  - [ ] 判断を後回しにした場合の影響まで説明されている
- 役割を明文化する
  - [ ] 「いつ、どこで、誰が」判断するのかが、各テーマで決まっている
  - [ ] 設計済みの案ではなく、業務に基づいた選択肢として説明されている
  - [ ] 「決定の記録」「確認の場」がセットで運用されている
- 意思決定プロセスを設計する
  - [ ] IT部門が選択肢を整理し、「どの判断が現場に適しているか」を分かりやすく提示している
  - [ ] 判断できなかった事項が、自動的に次の意思決定MTGに送られる仕組みがある
- 意思決定を「リスク」ではなく「役割」として設計する
  - [ ] 判断に失敗したら現場の責任になる、といった空気がない
  - [ ] 意思決定の前提（条件や製薬）が共有されている

### Rule6.本質的に必要な機能に絞ってリリースする勇気を持つ

- MUSTの基準は「成果」で決める
  - [ ] 各機能について「売り上げ」「コスト削減」「業務改善率」などの具体的な成果と紐づいた理由が説明されている
  - [ ] なぜそれがなければ業務が成立しないのかが、現場の言葉で語られている
  - [ ] MUST/WANT/不要(NONE)の分類基準がチーム全体で共有・明文化されている
- システム構築難易度を後で考える
  - [ ] 優先順位の初期判断は、業務インパクトを基準に決めている（技術的難易度は加味していない）
  - [ ] IT部門は「難しいからやらない」ではなく、「どうすればできるか」を検討する前提になっている
- MUST機能だけのプロトタイプで安心を可視化する
  - [ ] MUST機能だけで構成されたプロトタイプが、業務フローに沿って現場で検証されている
  - [ ] 現場が「この範囲でも業務は回せそうだ」と体感ベースで納得している
- 「後から追加できる」設計と文化を明示する
  - [ ] 初期段階から段階的リリース計画が共有されている
  - [ ] WANT機能を「今はやらないが将来的に追加検討するリスト」として整理・管理している
  - [ ] 現場が「今言っておかないと入れない」という不安を持たずに要望を整理できている

### Rule7.開発経過を利用者と共有する

- 進捗、課題をリアルタイムで可視化する
  - [ ] タスクや課題の進捗が、現場からいつでも確認できる状態になっている
  - [ ] 可視化された進捗や課題が、現場との対話のきっかけになっている
  - [ ] 現場が「何を進んでいて、何が止まっているのか」を自分の目で把握できている
- コミュニケーションをすべてオープンにする
  - [ ] 議論の履歴や判断の背景が、現場からも見える状態になっている
  - [ ] 「決まっていないこと」や「迷っていること」も共有されている
  - [ ] 現場からの質問や指摘がチャットや定例の中で自然に出てくる雰囲気がある
- プロダクトを「途中の状態でも」見せる
  - [ ] モックアップや試用環境などを早い段階で現場に提供している
  - [ ] 実際に現場が触っていて、気づきをフィードバックできる状態を作っている
- フィードバック内容をルール化し、誰でも見えるようにする
  - [ ] 出された要望や懸念が一覧化され、誰でも確認できる状態になっている
  - [ ] 各要望の対応状況（対応可／保留／対応不可）とその理由が記録されている
  - [ ] フィードバックが「検討されたうえで決まった」ことが現場に明確に伝わっている

## 「予算超過」を防ぐ極意

### Rule8.技術的な検証を徹底する

- 事業部門が判断できる技術リスク情報を提示する
  - [ ] 技術的な不確実性やリスクが、事業部門にとって理解可能な表現で整理されているか
  - [ ] 「この構成なら可能」「この条件が満たされていれば実現可能」など、前提と代替案がセットで提示されている
  - [ ] 検証の必要性や実施可否を判断するための情報（期間、費用、体制）が事前に共有されている
- プロトタイプによる技術検証を行う
  - [ ] 業務への適合性や技術的な前提を確認できる簡易プロトタイプが作成されている
  - [ ] プロトタイプによって「そのまま進めてよい部分」と「検証すべき部分」の見極めが行われている
  - [ ] プロトタイプ検証対象の発見・整理にも機能している
- 検証過程の透明化と共有で意思決定を早くする
  - [ ] 検証の進捗状況や中間結果が、定期的に関係者共有されている（非エンジニアにも伝わる形で）
  - [ ] 検証結果が、要件や構成の判断につながる意思決定材料として活用されている
  - [ ] 検証で得られた知見や製薬事項が、設計やスケジュール、コスト見積に反映されている

### Rule9.「トレードオフ」という発言を１００回する

- IT部門から率先してトレードオフを頻度良く使う
  - [ ] 要件に対して「できる・できない」だけでなく、複数の選択肢とその影響を提示している
  - [ ] 設計・レビュー・会議などの場で、「トレードオフ」「優先順位」「制約」という言葉を頻繁に使っている
  - [ ] 技術的な判断を一方的に伝えるのではなく、選択の材料として構造化して提示している
- トレードオフの判断を事業部門が実施する
  - [ ] 意思決定の主体を明確にし、事業部門に判断をゆだねる構造を作っている
  - [ ] 判断に必要な除法（選択肢、影響、前提条件）をあらかじめ整理して共有している
  - [ ] 選んでもらうだけでなく、選べる状態に整えることを意識している
- 「妥協」ではなく「最適解選択」としてトレードオフを理解する
  - [ ] トレードオフが「削る」「我慢する」ではなく、「もっとも価値ある選択をする」行為として認識されている
  - [ ] 決定理由を「納得感のある説明」で言語化し、関係者間で共有している
  - [ ] 各判断がプロジェクト目的や価値との関係で説明できるようになっている
- 選択肢を整理して判断基準を明示する
  - [ ] 重要な意思決定に際し、常に複数の代替案を整理して提示している
  - [ ] 各案に対して、コスト、期間、業務影響、リスクなどの評価指標を用いて比較している
  - [ ] 「AかB」ではなく、「Aならこうなる、Bならこうなる」と条件付きで説明している

### Rule10.ビジネス成長にこだわりを持つ

- ビジネス判断につながる前提情報を事業部門から引き出す
  - [ ] 業務の頻度、停止許容時間、影響額、法的制約などの前提情報を、要件ごとに明文化できている
  - [ ] 技術部門は「何を聞くべきか」を事前に整理し、業務側が答えやすい質問の形でヒアリングしている
  - [ ] 設計の意図や判断材料を支える業務インパクト情報が、テンプレートやシートに記載されている
- 設計判断の担当を決め、妥当性をビジネス価値で合意する
  - [ ] 「費用に対する意思決定は事業側」「構成選定は技術側」といった判断者が明確になっている
  - [ ] 判断が必要な場面では、前提条件・判断者・判断期限が合意され、記録に残されている
- 技術判断は構成とコストのセットで共有し、ビジネス視点で選択する
  - [ ] 技術案ごとに、初期費用・運用費用・償却期間などが明示されたコスト情報が添えられている
  - [ ] クラウド費用、Saasライセンス、監査対応などの非人件費が設計案に反映されている

### Rule11.エンジニア・デザイナーを要件定義に入れる

- 要件定義チームにエンジニアとデザイナーを必須メンバーとして組み込む
  - [ ] プロジェクト計画書に必須メンバーとして明記している
  - [ ] 参加頻度・役割・レビュー権限を事前に合意している
  - [ ] 部分的な質問対応にとどまらず、全体設計を見据えて判断機会を確保している
- エンジニアとデザイナーは自分たちで必要な情報をとりに行く
  - [ ] 自分で一次情報を取りにいっている
  - [ ] 技術・UI/UXの視点から、エンジニア、デザイナーが自分で能動的に質問している
- 要件定義の段階でプロトタイプや技術検証(PoC)を実施する
  - [ ] プロトタイプやPoCを要件定義フェーズの正式工程に組み込んでいる
  - [ ] デザイナーによるUI/UX検証で改善点を即時反映できている
  - [ ] エンジニアによる技術検証で性能・連携・実装可否を早期に確認している

  ### Rule12.小さい単位の見積りを徹底する

- 専門家が要件定義を詳細化する
  - [ ] 機能をプロトタイプ作成や技術検証ができるレベルまで分解できている
  - [ ] 未確定要件を「仮置き条件」として記録し、確定期限と責任者を設定している
  - [ ] 要件の依存関係を可視化し、どの確定がどの見積に影響するか整理している
- リスクバッファを適切に設定し管理する
  - [ ] バッファに明確な根拠（リスクの影響度や想定ケース）を示している
  - [ ] 仕様確定・検証完了など、バッファを解消できる条件を事前に設定している
  - [ ] バッファ解消に向け、事業・法務・セキュリティなど関係部門と役割分担を合意している
- 見積根拠を明文化する
  - [ ] 算出方法・前提条件・補正係数を文書化し、説明可能な形にしている
  - [ ] 機能ごとのコストをリスト化し、事業部門が優先順位を判断できる状態にしている
  - [ ] 根拠を関係部門と共有し、第三者レビューで妥当性を確認している

### Rule13.勇気を出して「できない」と伝える

- 「できない」とセットで前提条件を示す
  - [ ] 技術・予算・スケジュールの制約を、数値や条件で明文化している
  - [ ] 制約をあいまいな言葉ではなく、具体的な事実で説明している
  - [ ] 制約条件と代替案をセットにして関係者へ共有している
- 専門用語を翻訳し、ビジネス側に判断を委ねる
  - [ ] リスクを事業部門が理解する内容で提示されている
  - [ ] 文書だけでなく会話の場を持ち、双方向で理解を深めている
- 意思決定者を巻き込み、担当者レベルで利害があることを調整しない
  - [ ] 要件定義の場を「現場で洗い出す場」と「意思決定の場」に分けて設計している
  - [ ] 利害が絡む要件は担当者同士で結論を出さず、必ず意思決定者に引き上げている

## 「遅延」を防ぐ極意

### Rule14.全成果物を透明化する

- 成果物をリアルタイムで公開する
  - [ ] 常に最新版が１つのURLで参照できる状態になっている
  - [ ] 公開が日常の行為として定着しており、特別なイベントになっていない
  - [ ] コメントや修正履歴が成果物と紐づけて残されている
  - [ ] 意思決定者や他部門も必要に応じて最新版を直接確認できる
- 途中で共有することへの不安を和らげる
  - [ ] 会議で途中経過の共有が行われている
  - [ ] レビューが改善点を探すための場として運営されている
  - [ ] マネジメント層が途中段階の共有を評価するフィードバックを行っている
- 成果物を基準に進捗会議を運営する
  - [ ] 会議で成果物を画面に映しだし、全員が同じものを確認している
  - [ ] 会議の結論が具体的な修正や対応内容して明文化されている
  - [ ] 意思決定者が成果物を直接確認し、承認が速やかに進んでいる

### Rule15.すべてのやり取りを透明化する

- チャネルを統一し、やり取りを一元化する
  - [ ] 情報をやり取りする場所（課題管理ツールなど）が明確に定義されている
  - [ ] 事業部門・IT部門を含む全関係者がその情報源にアクセスできる
  - [ ] Slackやメールは通知・周知に限定し、一次情報は必ず情報源に集約されている
- 議論や質問をオープンに残す文化を育てる
  - [ ] 「社内で固めてから報告します」といった進め方が常態化していない
  - [ ] オープンに残されたやり取りがほかのメンバーにとって役立つと認識されている
  - [ ] 意思決定者自身がオープンに議論を残す姿勢を示している
- やり取りを構造化し検索可能にする
  - [ ] ラベル・タグ付けなどの分類ルールが明確で、全員が同じ基準で活用している
  - [ ] 関連情報がひとまとめに検索できる場所に保存されている
  - [ ] 過去のやり取りが検索で追える状態になっている

### Rule16.遠慮せずに確認する文化をつくる

- 意思決定者が確認を奨励する姿勢を示す
  - [ ] 意思決定者が「確認は歓迎される」と明言している
  - [ ] 会議で意思決定者が自らが率先して確認質問を行っている
  - [ ] 確認を行った人がポジティブに評価されている
- 会議設計に確認の場と心理的安全性を組み込む
  - [ ] アジェンダに「懸念・確認事項」の時間が組み込まれている
  - [ ] 出された確認が否定されず、建設的に扱われている
  - [ ] 会議外で出た懸念（雑談・終了後の声）が正式に拾われている
- 確認のフレームワークを活用する
  - [ ] 確認事項は「何を確認するか」が明確に書かれている
  - [ ] その確認に伴うサービス影響が定性・定量で整理されている
  - [ ] 影響範囲(部門・業務・顧客)が明示されている
  - [ ] 確認が意思決定の判断材料として機能する形になっている

### Rule17.IT部門の業務理解と徹底した牽制を行う

- 業務を深く理解して牽制機能を成り立たせる
  - [ ] 業務フローを自分の言葉で説明できる
  - [ ] 実際の現場オペレーションを観察・体験した経験がある
  - [ ] 事業部門が重視するKPIや評価指標を理解している
- 牽制機能をレビュー工程へ組み込む
  - [ ] レビューを週次または隔週のサイクルで実施している
  - [ ] 会議準備の負担が過大化せず、日常サイクルで自然にレビューできている
- 事業部門と対等に議論する文化を育てる
  - [ ] IT部門が「業務を理解したパートナー」として認識されている
  - [ ] 事業部門が疑問や懸念を素直に口にできる雰囲気がある
  - [ ] 会議での牽制や品質を高める共同作業として機能している

### Rule18.意思決定は一人に集約する

- 事業オーナーを明確化する
  - [ ] プロジェクト開始時に「最終意思決定者＝事業オーナー」が明文化されている
  - [ ] 体制図や役割分担表にオーナーの立場と責任が明確に記載されている
  - [ ] オーナーが事業的なリスクを引き受ける立場にあることを全員が理解している
- 情報集約の仕組みをつくる
  - [ ] 成果物、議論、議事録、ログなど、すべての情報がオーナーに届く仕組みがある
  - [ ] 情報が「報告者によって取捨選択された断片」ではなく、全体をオーナーが閲覧できる状態になっている
  - [ ] 情報はリアルタイムで更新され、オーナーが常に最新の状態を参照できる環境が整っている
- 情報を取りに行く姿勢を見せ、透明性を生み出す
  - [ ] オーナー自身が受け身にならず、自ら情報にアクセス、確認している
  - [ ] 成果物や議論ログがオープン化され、オーナーが直接参照できる状態になっている
  - [ ] オーナーの主体的な行動が現場に伝わり、「情報は常にみられている」という意識が共有されている

### Rule19.優先度判断レコードを活用する

- 意思決定ログの運用ルールを定義する
  - [ ] 「必ず記録する」というルールがチーム全体に共有されている
  - [ ] 「なぜえその結論に至ったのか」を必ず残している
  - [ ] ログの置き場所が一元化されている
- 意思決定ログを検索可能にする
  - [ ] 記録が時系列で整理されている
  - [ ] 論点に応じたタグが付与されている
  - [ ] 入力が簡単で、現場に負担がない
- 優先度判断テンプレートを導入する
  - [ ] 最小項目の項目（決定内容・選択肢・理由）が揃っている
  - [ ] 再評価のタイミングを明記できる
  - [ ] テンプレートを定期的に見直して改善している

### Rule20.意思決定者が決める覚悟を持つ

- 少ない情報で決める覚悟を持つ
  - [ ] 情報が不完全でも、判断を先送りせず結論を出している
  - [ ] 判断を下すことで、次の行動が動き出している
- 普段から情報収集を徹底する
  - [ ] 意思決定者自身が、現場や市場の情報を継続的にキャッチアップしている
  - [ ] 情報収集を担当者任せにせず、自分でもアクセスしている
  - [ ] 緊急の判断にも対応できるよう「即決できる状態」を維持している
- 判断基準を自分なりに決める
  - [ ] 「この基準で決める」という判断軸を明文化している
  - [ ] 判断の基準が一貫して適用されている
  - [ ] 全員の合意ではなく、推進者として責任をもって基準を貫いている
